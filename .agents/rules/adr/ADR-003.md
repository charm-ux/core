# ADR-003: Register components through a scoped registry

**Date:** 2026-07-19

This ADR is a worked example of the format in [ADR-002](./ADR-002.md); it records a decision
already embodied in the codebase (`packages/core/src/utilities/scope.ts`) and codified as
[CHARM-002](../internal/CHARM-002.md).

## Context

Custom element tag names are a **global, single-registration** namespace: `customElements.define('ch-button', …)`
can only run once per name per document, and a defined name can never be un-defined without a
page reload. Charm is a shared library that consumers embed alongside other code, and a single
page may legitimately load:

- more than one **version** of Charm (e.g. a host app and an embedded widget on different
  release cadences), and/or
- more than one **instance/origin** of the library.

If every component called `customElements.define()` (or used the `@customElement` decorator)
at import time, the second copy to load would throw on the already-registered tag, and there
would be no way to give consumers a custom prefix.

We considered:

1. **Global `customElements.define` / `@customElement`** — simplest, but collides across
   versions/origins and hardcodes the `ch-` prefix.
2. **Build-time renaming** — rename tags per consumer during their build; heavy tooling
   burden and no runtime coexistence.
3. **A runtime scope registry** — components declare a `static baseName`; a scope object owns
   prefix/suffix and performs registration, tracking collisions in a shared global.

## Decision

Use the runtime scope registry (option 3). Components never define themselves. Each concrete
component declares `static override baseName = '<name>'`, and `project.scope.registerComponent()`
builds the tag as `${prefix}-${baseName}${suffix ? '_' + suffix : ''}` (default prefix `ch`).

Collisions are tracked on a shared `window.CharmComponents.scope` (a `tagMap` and
`baseNameMap`) so multiple versions/origins can coexist, and registration is idempotent: an
already-registered tag is skipped rather than re-defined. Consumers can supply a `suffix` to
scope an entire library instance (`<ch-button_support>`). This is enforced by
[CHARM-002](../internal/CHARM-002.md).

## Consequences

**Positive:**

- Multiple Charm versions/instances coexist on one page without tag collisions
- Consumers can re-scope the whole library via prefix/suffix
- Registration is idempotent and never throws on double-registration

**Negative:**

- Components cannot be authored with the idiomatic `@customElement` decorator; contributors
  must learn the `baseName` + `index.ts` registration pattern
- A component that forgets `static baseName` fails silently at runtime (logs a console error
  from `scope.ts`) rather than at build time
- Scope state lives on a shared global (`window.CharmComponents`), which must stay backward
  compatible across versions

**Assumptions:**

- The default `ch` prefix is stable; changing it is itself an architectural decision requiring
  a new ADR.
