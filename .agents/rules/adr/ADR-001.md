# ADR-001: When to write an ADR

Write an Architecture Decision Record when making decisions that:

- **Affect multiple packages or consumers** — changes to shared APIs, token structures, scope
  registration, or the base-class hierarchy that `packages/core`, `packages/theming`, and
  consumers all depend on
- **Are difficult or costly to reverse** — dependency choices, the tag-scoping model, event
  contracts, breaking changes to the custom-elements manifest
- **Involve trade-offs that future readers might question** — "why didn't they just use
  `customElements.define`?"
- **Establish patterns others should follow** — new base classes, theming conventions,
  recommended authoring approaches

**Do write an ADR for:**

- Adding a dependency that affects the public API or bundle
- Changing the token naming convention or theming contract
- Introducing or reshaping a base class in the `CharmElement` hierarchy
- Deprecating a component in favor of a new pattern
- Choosing between competing implementation approaches with meaningful trade-offs

**Don't write an ADR for:**

- Bug fixes
- Refactors that don't change behavior
- Adding a new component that follows the existing patterns (`pnpm plop` scaffolding)
- Minor dependency updates

When in doubt, ask: "Will someone six months from now wonder why we did this?" If yes, write
an ADR.
