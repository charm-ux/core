# A11Y-010: Reflect disabled state with `aria-disabled` on the widget host, and keep it in sync

A disabled widget must not present as focusable/actionable to assistive tech. Use
`aria-disabled` on the element that carries the widget's `role` — the host, not an inner
decorative control — and drive it reactively from the `disabled` property so it is applied
_and removed_ as the state changes. Don't render `aria-disabled` once from a template
condition; a stale `aria-disabled="true"` left behind after re-enabling makes a working
control look disabled to AT users forever.

**Do:**

```ts
// menu-item.ts — aria-disabled belongs on the host (role="menuitem"), not the inner .base
public override willUpdate(props: PropertyValues) {
  if (props.has('disabled')) {
    this.setAttribute('aria-disabled', String(!!this.disabled));
  }
}
```

**Don't:**

```ts
// Once set, this is never removed when `disabled` goes false — a re-enabled tab/menu-item
// stays announced as disabled.
render() {
  return html`<div class="base" aria-disabled=${this.disabled}>...</div>`;
}
```

Native controls (`<button disabled>`, `<input disabled>`) already convey their disabled state
to AT; only add `aria-disabled` where the interactive element is a non-native widget with an
explicit `role` that native disabled semantics don't reach.
